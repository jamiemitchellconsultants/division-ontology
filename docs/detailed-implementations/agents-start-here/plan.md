## Decisions this plan settles

The questions the architect passed to the developer, answered from the code as it stands on 24 November 2026:

- **Assertion wording.** The contract tests match short, load-bearing phrases (setup names, declined-default words, the three answer states, canonical file names), following the existing style of `test/onboarding-docs.test.mjs` (regexes over `readFileSync`, no structure parsing). Prose around those phrases may be edited by stewards without breaking tests; renaming a setup, a default, or a state breaks them deliberately.
- **Survival needs no code change.** `templateCopy()` in `test/init-division.test.mjs` already copies `docs/` wholesale, and `scripts/init-division.mjs` removes only `docs/features/one-action-source-onboarding`, `docs/superpowers`, and `docs/detailed-implementations` (`templateHistory`). `docs/agents-start-here.md` therefore survives; Task 4 only asserts it. Note the consequence for this plan’s own files: a division copy does **not** keep `docs/superpowers/plans/agents-start-here/` or `docs/detailed-implementations/agents-start-here/` — that is expected; the runbook it must keep is `docs/agents-start-here.md`.
- **CODEOWNERS transfer needs no code change.** `rewriteCodeOwners` in `scripts/init-division.mjs` rewrites every non-comment line to `@<steward>…`, preserving only the path token. Adding `/docs/agents-start-here.md` in Task 3 is sufficient for B16; Task 4 asserts the rewritten line explicitly because the existing generic loop would also pass if the line were missing.
- **Template creation command.** `gh repo create <owner>/<name> --template jamiemitchellconsultants/division-ontology --public --clone` — verified against `gh repo create --help` on gh 2.104.0 (`-p, --template repository`; `-c, --clone`). The document also names GitHub’s **Use this template** button as the equivalent manual route, and requires the recorded public-confirmation before either is used.
- **Where the setup record lives.** In the agent’s report to the founder at handover, in the table form Task 2 writes into the document. It is committed nowhere: the new repository records only the resulting `division.json`, CODEOWNERS, and catalog, and the founder’s repository records nothing. This keeps secrets out of git by construction (B12) and matches the architect’s “conversation artefact” component.

## The document Task 2 writes

`docs/agents-start-here.md`, titled “Agents start here”, in this order. Wording may vary; the named items, tables, and defaults may not.

1. **Who this is for.** An agent asked to “Create a division from this template”. Link back to `AGENTS.md` for everything after creation.
2. **1 — Prompt first, create nothing yet.** Two tables the agent completes before any creation:
   - Required: target owner/name; division namespace; steward logins; confirmation that a public repository publishing source ontologies is intended. “If any required answer is missing, stop and ask. Never invent one, and never default one.”
   - Optional (ask each by name, state the declined default): runtime knowledge workspace → declined: catalogue-only; embedding/semantic-search provider (only when the workspace is accepted) → declined: no semantic search, catalogue and text search only, with one sentence that similarity is discovery for human judgement and never creates a link or equivalence; C4 impact pilot → declined: not set up; granted-source onboarding via the dedicated source-read App → declined: steward-registered sources only; catalogue auto-merge → declined: catalogue pull requests wait for steward review.
   - Answer states and the setup record: a table with one row per choice above and columns `Choice | Answer (accepted / declined / defaulted — not answered) | Notes`. “An unanswered optional prompt takes its declined default and is recorded as defaulted — not answered, never as accepted or declined. The record holds choices and pending steps only — no token, private key, or password.”
3. **2 — Create and clone.** The `gh repo create … --template … --public --clone` command with the recorded owner/name, or **Use this template** then clone. “Work in the new clone from here. If creation fails, stop; initialise nothing in the template repository.”
4. **3 — Initialise once, before any sources.** `npm ci`, then `npm run init-division -- --namespace <recorded namespace> --steward <each recorded steward>`. Then verify and report: `division.json` holds the recorded values; the core and CODEOWNERS use them; Narrative empty; `sources.json` empty; catalog rebuilt in the new namespace. Review the diff before any commit; commit only when the founder asks.
5. **4 — Automation and chosen setups.** Follow [the automation setup](../automation-setup.md) for the two Apps, variables/secrets, required checks, and auto-merge last (only when accepted). For each accepted optional setup, link its canonical document instead of instructing it: workspace → the workspace runbook (`docs/features/runtime-knowledge-workspace/05-runbook.md`); embeddings → `docs/adding-embedding-search.md`; granted sources → the automation setup’s source-read App section. “Where a step needs an App administrator, a branch-rule change, a steward approval, or a source owner’s publication consent that you do not have, record it as pending, name who must do it, and do not report the setup complete. Never grant yourself App access; never put credentials in files or command arguments.”
6. **5 — Verify the first sync.** Trigger or await `Sync division catalog`; report the workflow result or the generated catalog pull request. A failed source or access step is fixed at its cause before retrying, and leaves the published catalog untouched.
7. **6 — Hand over.** Report the completed setup record (required choices, every optional setup’s state, pending hand-offs — never “skipped”), then point onward: `AGENTS.md` for ongoing agent requests (“Add…”, “Join…”, “Sync division ontology now”), `GOVERNANCE.md` for shared terms and links, the automation setup for App and branch administration, and the workspace runbook when the workspace was chosen. State that this document (`docs/agents-start-here.md`) stays in the new repository, owned by its stewards, for the next agent.

## Task notes

- **Task 1** appends to `test/onboarding-docs.test.mjs` only; the five existing tests must keep passing throughout. The `assert.doesNotMatch(doc, /create a link from a (similarity )?match/i)` line pins B14’s negative: check the document’s own similarity sentence does not trip it when Task 2 lands.

- **Task 4** inserts its two assertions directly after the existing `assert.ok(existsSync(join(root, 'docs/features/runtime-knowledge-workspace/05-runbook.md')));` line in the first init-division test, reusing its `root`, `existsSync`, and `readFileSync`. The rename-and-fail check proves the survival assertion bites; restore the filename before committing.
- **Task 5** is verification only. The scratch walkthrough uses invented values (`https://example.test/sales-division#`, `sales-steward`) in `$TMPDIR`, never a real GitHub repository (U3), and is deleted afterwards. Acceptance walkthroughs for a live division belong to the user phase, not this build.
